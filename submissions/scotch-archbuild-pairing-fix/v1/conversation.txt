
It passes an **unbased** vertex index to `mapDomain`, but `mappdat.parttax` is a **based** array. Everything downstream of that mismatch is built on the wrong vertex-to-terminal association. Here is the full chain.

## The indexing inconsistency

`mapDomain` is `&map->domntab[map->parttax[idx]]` (`mapping.h:162`) — it just indexes `parttax` with whatever you give it.

How `mappdat.parttax` is indexed everywhere else in this function:

- `arch_build.c:186`: `mappdat.parttax -= tgtgrafptr->baseval;` — the array is explicitly rebased, so valid indices are `[baseval, baseval + vertnbr)`.
- The write sites during the recursive bipartitioning loop use based indices:
  - `arch_build.c:267` (job graph without `vnumtax`): `mappdat.parttax[actvertnum]` with `actvertnum` running from `baseval` to `vertnnd` — based.
  - `arch_build.c:259` (induced job graphs): `mappdat.parttax[actgrafdat.s.vnumtax[actvertnum]]`. Induced-graph `vnumtax` entries are **based** original-graph vertex numbers — `graph_induce.c:184` stores `orgvertnum` which iterates from `baseval`, and `graph_induce.c:355` composes nested inductions back to the root graph, preserving basing.
- Every other `mapDomain` call site in libscotch (`kgraph_map_rb.c:630`, `kgraph_map_rb.c:651`, `kgraph_map_fm.c:670`) passes a based vertex number directly.

Line 309 alone subtracts `baseval` first. Since `parttax` was already rebased, `mapDomain(&mappdat, tgtvertnum - baseval)` actually reads `parttax_orig[tgtvertnum - 2*baseval]`.

With `baseval == 0` the two conventions coincide and nothing is visibly wrong — which is why the common C-API path never trips over it. With `baseval == 1` (the Fortran API, or any C caller that builds its architecture graph base-1, which `SCOTCH_graphBuild` fully permits):

1. **For the first terminal** (`tgtvertnum == 1`): it reads `parttax_orig[-1]` — an out-of-bounds heap read of the word *before* the block allocated at `arch_build.c:171`. That garbage value is then used as an index into `domntab`, which holds only `termdomnbr` entries — a second, wild out-of-bounds read. The `termnum` extracted from that fake `ArchDom` is arbitrary.
2. **For every other terminal**: it reads the domain of vertex `tgtvertnum - 1` — a *different* vertex. The terminal record built at lines 307–309 therefore combines the label and weight of vertex *v* with the terminal number belonging to vertex *v − 1*.

## Why this corrupts the architecture, not just its quality

The recursion in the job loop splits domains until every job is a singleton, so at the end the map "target vertex → terminal number" is a bijection onto the leaves of the `varcmplt` binary tree (`archVcmpltDomBipart` numbers them root = 1, children `2n`/`2n+1`). The `num` field is not a cosmetic label — it is the **position in the recursive-bisection tree**, and `archDecoArchBuild2` uses it as a direct array index:

- `arch_deco.c:145-147`: `domverttab[num - 1].labl/.size/.wght = ...`. With the shifted assignment, the last vertex's true terminal number is never assigned to any record, while the garbage `num` from step 1 lands somewhere arbitrary. Two outcomes, both bad:
  - **Duplicate `num`**: two physical vertices write the same tree slot; one processor silently vanishes from the architecture. The upward accumulation (lines 150–159) then computes wrong `size`/`wght` for every ancestor. The sanity check `domverttab[0].size != termdomnbr` (`arch_deco.c:161`) only exists under `SCOTCH_DEBUG_ARCH1` — production builds proceed silently.
  - **Hole in the tree**: a leaf slot inside the used region stays `ARCHDOMNOTTERM` with `size 0`, so some internal domain claims `size k` while its children sum to `k − 1`. Later, when a mapping recursively bipartitions over this architecture, that inconsistency yields empty subdomains or terminal lookups resolving to the wrong `.labl`.
- **`termdommax` itself** (lines 310–311, the lines you pointed at) is computed over these corrupted `num` values. If the garbage `num` is huge, `archDecoArchBuild2` allocates `termdommax * (termdommax−1)/2` distance slots — an absurd allocation, or an integer overflow in the size computation leading to an undersized buffer. If the garbage is negative, it survives the `> termdommax` comparison and `domverttab[num - 1]` at `arch_deco.c:145` becomes an out-of-bounds **write** — heap corruption. The debug guard at `arch_deco.c:138` (`num > termdommax`) again only exists under `SCOTCH_DEBUG_ARCH1`, and doesn't catch negative values anyway.
- **The distance matrix gets mis-keyed.** The BFS at lines 315–357 correctly measures distances between the `.labl` vertices, but `arch_deco.c:171` stores each distance at `archDecoArchDist(arch, num_i, num_j)` — indexed by the wrong terminal numbers. So the measured distance between processors *u* and *v* is attached to the tree pair for *u−1* and *v−1*. In the duplicate-`num` case, `archDecoArchDist(d, n, n)` evaluates `(n−1)(n−2)/2 + n − 1`, which aliases an unrelated pair's cell — silently clobbering other distances.

## Net effect on the user

Any partitioning later computed with `SCOTCH_graphMap` onto this deco architecture is built from a decomposition tree whose leaf labels, weights, and distances are shifted relative to the bisection that was actually performed. Concretely: vertex loads are balanced against the wrong processor capacities (weight of processor *v* sits at *v−1*'s tree position), communication costs are evaluated against distances between the wrong processor pairs, one processor can be missing from the architecture entirely while another appears twice, and the returned `parttab` contains processor labels inconsistent with the architecture graph the user described. That's an invalid partitioning even when it doesn't crash — and with the base-1 first-vertex path it can also crash or corrupt the heap outright.

The fix would be to pass `tgtvertnum` unmodified (matching all other `mapDomain` call sites), since `mappdat.parttax` is already rebased.

Two side observations while I was in there, distinct from this bug: the weighted "BFS" at lines 332–352 uses a plain FIFO queue while accumulating edge loads (`arch_build.c:348`) — first-visit distances aren't shortest paths on an edge-weighted target graph, so `termdisttab` is only an approximation there (a quality issue, and Dijkstra territory, but it doesn't invalidate the architecture the way the basing bug does). And note the whole thing is invisible in the standard base-0 test suites — a good hegel-c angle for `tests/irl/scotch` would be a property comparing the deco architecture built from the same graph at base 0 vs. base 1 (they must be identical), which also makes the `parttax_orig[-1]` read trip ASan deterministically.

Interesting — this fixes the crash but I don't think it's the right fix. It replaces the per-vertex domain lookup with an index-based one that assumes an invariant the job loop doesn't provide. Let me lay it out.

## What the patch gets right

`&mappdat.domntab[termdomnum]` removes the `parttax` read entirely, so the base-1 disaster chain from before (OOB read of `parttax_orig[-1]` → wild `domntab` index → garbage/negative `num` → heap-corrupting write in `archDecoArchBuild2`) is gone. It also has a nice structural property: at loop end `domnnbr == termdomnbr` (every split adds exactly one domain, and the recursion runs until every domain is a singleton), so `domntab[0..termdomnbr-1]` enumerates each terminal leaf domain exactly once. The `num` values are therefore a clean bijection onto the leaf set — no duplicates, no holes, `termdommax` sane, debug checks pass.

## What it gets wrong

The patch asserts that **domain index `i` is the domain of terminal vertex `i`** — i.e., `parttax[tgtvertnum] == termdomnum`. But domain indices are assigned in *split-creation order* driven by the LIFO job stack (`arch_build.c:271-286`), which has no relationship to vertex rank. The correct pairing is exactly what `parttax` records at lines 259/267.

Concrete counterexample, base 0, five vertices, even with perfectly contiguous bipartitions (e.g. a path 0–1–2–3–4):

1. `job0`={0..4} splits into {0,1,2}/{3,4}. Subjob gets **dom1={3,4}**. Stack (joborg pushed last, popped first): [`job0`={0,1,2}, `job1`].
2. Pop `job0`={0,1,2} → {0,1}/{2}: **dom2={2}**. Push joborg {0,1}.
3. Pop `job0`={0,1} → {0}/{1}: **dom3={1}**.
4. Pop `job1`={3,4} → {3}/{4}: **dom4={4}**, job1 keeps **dom1={3}**.

Ground truth (`parttax`): vertex 1 → dom3, vertex 3 → dom1. The patch pairs vertex 1 ↔ dom1 and vertex 3 ↔ dom3 — **swapped**, in the most vanilla case imaginable. Tracing the vcmplt leaf numbers (root 1, children `2n`/`2n+1`): correct pairing is v0↔8, v1↔9, v2↔5, v3↔6, v4↔7 — note {8,9} are siblings holding the topologically adjacent v0,v1, exactly what `deco 0` is for. The patched pairing puts v3 at leaf 9 instead, so the subtree that the bisection built around {v0,v1} now claims to contain {v0,v3} — processors the bisection deliberately put in *opposite* halves.

## Consequences

The mispairing is *self-consistent*: leaf `num_i` carries `labl` v_i, weight w(v_i), and the leaf-pair distance slots (`arch_deco.c:171`) get the BFS distance between their own labels. Each processor appears exactly once with its correct weight and correct pairwise distances. So the architecture is **valid** — mappings won't crash, won't drop processors, and balance correctly.

What's silently destroyed is the entire point of building a deco architecture by recursive bisection: the tree hierarchy no longer groups topologically close processors, so the recursive-bisection mapper loses its structural guidance and communication quality degrades. And note this is a **regression at base 0**, where the old code (`parttax[tgtvertnum - 0]`) was fully correct — the patch trades "crashes at base 1, correct at base 0" for "never crashes, mispaired at every base whenever split order ≠ rank order," which is the typical case from 3 terminals up. All validity checks (even `SCOTCH_DEBUG_ARCH1`) still pass, so nothing flags it.

## The fix I'd expect

Keep the lookup, drop only the spurious rebasing — `parttax` was already rebased at line 186:

```c
termverttab[termdomnum].num = archDomNum (&archdat, mapDomain (&mappdat, tgtvertnum));
```

That matches every other `mapDomain` call site in libscotch and preserves the vertex→domain ground truth.

## How to confirm empirically

Two easy oracles, both good hegel-c properties for `tests/irl/scotch`:

- **Pairing check**: after `SCOTCH_archBuild` on a base-0 graph, compare the patched build against the pre-patch code at base 0 (which was correct there) via `SCOTCH_archSave` — on a path graph with ≥5 vertices the outputs should differ, proving the patch changed base-0 behavior.
- **Quality property**: build `deco 0` from a path/grid graph, then check that leaf siblings in the saved decomposition are graph-adjacent (distance 1 apart). Correct pairing satisfies this on a path; the patched code will violate it on the 5-vertex trace above.

One caveat in fairness to the patch: if there were an invariant forcing domain-creation order to follow vertex rank, it would be correct — but the LIFO stack plus "subjob takes the part not containing the first vertex" breaks that as soon as one branch goes deeper than the other, as the trace shows. ## How the oracle works

The blocker was that the mispairing is *permutation-consistent*: labels, weights, and leaf-pair distances all travel together, so every public-API self-consistency check passes on a mispaired architecture. The only violated relation is **tree structure ↔ labels**, and checking it requires knowing the true bisection. So the tests force it: a path graph whose edge distances all sit in [100, 199] (within a factor of 2, so after `graphIelo` inversion any single-edge cut beats any two-edge cut → parts stay contiguous), with each interval's median edge strictly largest (→ strictly cheapest cut). Under a correct build, sibling singleton leaves in the saved deco tree are the two ends of the last edge cut — path-adjacent, labels differing by exactly 1. The classic test adds a base-invariance oracle (base-0 and base-1 builds must match modulo the label shift).
